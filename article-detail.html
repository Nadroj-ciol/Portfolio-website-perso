✦ Génie Logiciel & Architecture

Concevoir une architecture logicielle modulaire et résiliente en milieu à connectivité intermittente

NDE Jordan L.
Technologue en Génie Logiciel · IUT Douala
📅 18 Octobre 2026 ⏱️ 7 min de lecture
Dans les contextes d'exploitation où le réseau Internet et l'alimentation électrique connaissent des coupures fréquentes, concevoir une application critique requiert de repenser l'architecture système de fond en comble.
[Article rédigé en français · Retours d'expérience du terrain]

1. Le défi : la dépendance aux connexions permanentes

La majorité des architectures cloud modernes supposent une latence réseau sous les 50ms et une disponibilité de 99.9%. Sur le terrain au Cameroun et en Afrique subsaharienne, qu'il s'agisse d'un hôpital ou d'une exploitation agricole, ces hypothèses échouent dès les premières heures de déploiement.

Lors du développement de Sister Schola ERP et d'AgroFlow SaaS, notre objectif prioritaire a été d'adopter le paradigme Local-First : l'application doit continuer à fonctionner à 100% de ses capacités même sans aucune connexion Internet active.

Principe fondamental : Tout événement de saisie (admission d'un patient, enregistrement d'une récolte, pesée) doit être écrit immédiatement dans le stockage local persistant et sécurisé avant même toute tentative d'émission réseau.

2. Modèle de synchronisation bidirectionnelle résiliente

Pour garantir la cohérence des données sans perte ni conflit d'écrasement, nous avons implémenté une file de messages d'événements (Event-Driven Queue) s'appuyant sur IndexedDB côté client et un gestionnaire de transactions ACID PostgreSQL côté serveur.

TypeScript / EventSyncEngine.ts Pattern Outbox Local-First 
interface SyncEvent<T = unknown> {
  id: string;              // UUID v4 unique généré localement
  aggregateType: string;   // Ex: 'STUDENT_ENROLLMENT' | 'PATIENT_ADMISSION'
  payload: T;
  createdAt: number;       // Timestamp UNIX côté client
  synced: boolean;
  retryCount: number;
}

// Transaction atomique locale avant synchronisation réseau
async function commitLocalFirst<T>(event: Omit<SyncEvent<T>, 'id' | 'synced' | 'retryCount'>) {
  const transaction = db.transaction(['outbox_queue', 'local_view'], 'readwrite');
  const record: SyncEvent<T> = {
    ...event,
    id: crypto.randomUUID(),
    synced: false,
    retryCount: 0
  };
  
  await transaction.objectStore('outbox_queue').add(record);
  await updateLocalOptimisticView(record);
  
  // Déclenchement de la synchronisation asynchrone en arrière-plan
  triggerBackgroundSync();
}

3. Résolution des conflits et horodatage vectoriel

Lorsque deux terminaux modifient simultanément une ressource hors-ligne, la stratégie naïve du Last-Write-Wins basé sur l'horloge système peut écraser des données cruciales en cas de désynchronisation NTP. Nous appliquons plutôt une résolution par type d'attribut combinée à un log d'audit immuable.

4. Résultats mesurés en production

  • Zéro perte de saisie lors des coupures de fibre optique ou réseau 4G.
  • Temps de réponse UI instantané (< 15ms) pour toutes les opérations utilisateur grâce au rendu optimiste.
  • Synchronisation silencieuse dès le rétablissement de la connectivité avec reprise automatique en cas de rupture de flux.
